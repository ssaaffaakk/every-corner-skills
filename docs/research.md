# Ask until certain, then build once

> **About this report.** This is the research done before the skills were built (November 2026), published so you can check the claims in the README. It was written for an early single-skill design called "plan-every-corner". The final design differs in a few places: the work was split into three separate skills, the interview has **no question budgets or checkpoint pauses** (it asks until the stopping rule passes, and the user can say "build now" at any time), and files live in `docs/every-corner/`. [How it works](how-it-works.md) describes what was actually built.

Nothing published today does all three jobs "plan-every-corner" wants, but every piece exists somewhere and the evidence agrees on how to fit them together. For the Interview mode, the published options run from hard-capped clarifiers (GitHub Spec Kit asks **at most 5 questions, one at a time, each with a recommended answer**) to open-ended "interview me until it's complete" prompts that **typically run 20-60 questions**. The research says models **under-ask by default**: more than 60% of code-model responses generate code instead of asking. It also says the count of questions matters less than picking the right ones: the best agents get the same information with **about half as many questions** because they explore the codebase first. For the Tour mode, no tool combines reading every corner, explaining it to a beginner like a friend, and proving what it covered. Hosted wikis such as DeepWiki are reported to hallucinate confidently and to drop folders without saying so. For permission prompts, users approve **93% of them**, warnings stop being read after the second exposure, and a crowded field of dangerous-command guards explains its verdicts to the agent rather than to a junior. The recommended design has five parts. First, a size triage step. Second, an uncapped but disciplined interview: ask only about things the user alone knows and that would change the code, track coverage in a ledger, and stop when every requirement has a testable acceptance criterion. Third, a three-level tour that never skips a directory silently. Fourth, a risk-scaled explanation layer that sits on top of an existing guard. Fifth, all state lives in files, and the build starts in a fresh session.

## Interview tools split between five-question caps and sixty-question marathons

Existing interview workflows fall into two camps, and the difference is mostly a dial setting rather than a different philosophy. The capped camp is led by GitHub Spec Kit. Its `/specify` command drafts the spec itself, tells the model to "make informed guesses based on context and industry standards", and allows **at most 3 `[NEEDS CLARIFICATION]` markers**. It ranks them by "scope > security/privacy > user experience > technical details" and lists defaults it should never ask about, such as data retention, performance targets and auth method ([spec-kit specify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)). Its `/clarify` command has the most rigorous selection logic in the field. It scans the spec against a **10-category taxonomy**, marks each category Clear, Partial or Missing in an internal coverage map, and keeps only questions whose answers "materially impact architecture, data modeling, task decomposition, test design, UX behavior, operational readiness, or compliance validation". It ranks those by an **Impact × Uncertainty** heuristic and asks **exactly one question at a time**. Each question carries a "Why it matters" line, a **Recommended** option with its reasoning, and 2-5 mutually exclusive choices; replying "yes" accepts the recommendation. Each answer is written into the spec immediately, and the session ends with a Resolved / Deferred / Clear / Outstanding coverage table ([spec-kit clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)). snarktank's create-prd takes the batch route: **3-5 lettered questions in one message**, answered as "1A, 2C, 3B" ([create-prd.md](https://raw.githubusercontent.com/snarktank/ai-dev-tasks/main/create-prd.md)).

The open-ended camp is now official Anthropic guidance. The Claude Code best-practices page recommends "Interview me until you could write the spec, then write it to SPEC.md". It describes Claude returning multiple-choice questions about unpinned parts until "the answers add up to a spec", then building in a **fresh session** "so the build begins with a clean context and a written definition of done". Later, a reviewer checks the diff against SPEC.md ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Thariq's viral version of the prompt says to interview "about literally anything" until complete. In VelvetShark's test it asked **32 questions for a bookmark manager**, and the author reports **20-30 questions typically and 40-60 for complex features**, which produced a 157-line SPEC.md after "a few minutes" of answering ([VelvetShark](https://velvetshark.com/stop-prompting-claude-code-let-it-interview-you)). obra/superpowers' brainstorming skill also has no numeric cap. It asks one question per message and prefers multiple choice. Before interviewing, it classifies the request as **Spike, Bounded or Architectural** and says the classification aloud; when in doubt it takes the heavier path. Before refining details it flags requests that need to be decomposed, because "Don't spend questions refining details of a project that needs to be decomposed first" ([superpowers brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)). The transport layer constrains every Claude Code design: `AskUserQuestion` takes **1-4 questions per call with 2-4 options each**, offers a free-text "Other" option, and is **not available inside subagents** ([Agent SDK user input](https://code.claude.com/docs/en/agent-sdk/user-input)).

|---|---|---|---|---|---|

Sources for the table: [Spec Kit](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md), [create-prd](https://raw.githubusercontent.com/snarktank/ai-dev-tasks/main/create-prd.md), [superpowers](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [VelvetShark](https://velvetshark.com/stop-prompting-claude-code-let-it-interview-you), [Agent OS](https://github.com/buildermethods/agent-os/blob/main/commands/agent-os/shape-spec.md), [Taskmaster](https://github.com/eyaltoledano/claude-task-master).

Other tools fill the gaps between these two camps. Cline's `/deep-planning` begins with "Silent Investigation" of the codebase before asking targeted questions, then hands the plan to a new task with a clean context ([Cline](https://docs.cline.bot/features/deep-planning.md)). Kiro generates `requirements.md`, `design.md` and `tasks.md` in **EARS notation** ("WHEN [event] THE SYSTEM SHALL [behavior]") and has the user review the documents, rather than interviewing first ([kiro.dev](https://kiro.dev/docs/specs/feature-specs/)). BMAD's elicitation skill now criticizes a draft instead of interviewing. Its method catalog sorts methods by direction (wrong, missing, premise, simplify, future, other-side) and includes an Edge Case Sweep over "empty, zero, maximum, malformed" ([BMAD methods.csv](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/core-tools/bmad-advanced-elicitation/assets/methods.csv)). Adoption is large: superpowers has **317,956 stars**, Spec Kit **149,906**, OpenSpec **74,909** and BMAD **55,397** ([GitHub API](https://api.github.com/repos/github/spec-kit)). Thariq's post drew **1.3M+ views in three days** ([VelvetShark](https://velvetshark.com/stop-prompting-claude-code-let-it-interview-you)).

User complaints point to the failure the skill must avoid: ceremony that does not match the size of the task. Thoughtworks' Birgitta Böckeler watched Kiro turn a small bug into "4 user stories with 16 acceptance criteria". She found Spec Kit's eight Markdown files "very verbose and tedious to review", and the agent still created duplicate classes despite having a spec ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Cursor users report that question mode "often appears when it is not needed", and staff confirmed it cannot be turned off ([Cursor forum](https://forum.cursor.com/t/option-to-turn-off-plan-and-question-mode/168110)). One critic argues that "AskUserQuestion is designed to narrow you down", because users who pick the offered options drift toward the predictable path. A commenter on the same post said Claude "used to question me infinitely" ([Robots Ate My Homework](https://robotsatemyhomework.substack.com/p/penny-moves-claude-askuserquestion)). The lesson is not that interviews are bad. It is that a skill needs a size triage step, a visible exit, a single compact spec file, and protection against anchoring the user.

## Research says agents under-ask, but question count is not the lever

The empirical case for a mandatory interview phase is strong. When HumanEvalComm made all 164 HumanEval problems ambiguous, inconsistent or incomplete, **pass@1 fell 35-52%**, and **more than 60% of responses still wrote code instead of asking** ([HumanEvalComm](https://arxiv.org/abs/2406.00215v2)). ClarifyCodeBench measured drops of **7.8-19.8 absolute points** from ambiguity on 419 LiveCodeBench tasks. Frontier models, including GPT-5 and Claude Sonnet 4.5, asked fewer questions than the annotated optimum and started coding early. Their resolution of multiple ambiguities in one task "drops near zero" ([ClarifyCodeBench](https://arxiv.org/pdf/2607.00711); [EmergentMind summary](https://www.emergentmind.com/papers/2607.00711)). In CMU's Ambig-SWE, models "almost never interact, even for severely underspecified inputs" unless prompted to. When they do interact, performance on underspecified tasks rises by **up to 74%**, and Claude Sonnet 4 recovers **89% of its fully-specified performance** ([Ambig-SWE](https://arxiv.org/html/2502.13069v3)). ClarifyGPT, which asks only after detecting ambiguity, raised GPT-4's MBPP pass@1 from **70.96% to 80.80%** ([ClarifyGPT](https://huggingface.co/papers/2310.10996)). Even an oracle answering every question perfectly left ClarifyCodeBench slightly below a complete written requirement ([ClarifyCodeBench](https://arxiv.org/pdf/2607.00711)). That is why the interview must end in a written spec, not a chat transcript.

The same studies show that asking more questions does not help by itself. In Ambig-SWE, Qwen 3 Coder asked **6.02 questions per task** against Sonnet 4's **4.03**, with similar resolve rates. The authors attribute Sonnet's efficiency to **exploring the codebase before asking**. DeepSeek's implementation-level questions "exceeded what the user knew" and wasted turns, and Haiku fell back on a rigid three-question template ([Ambig-SWE](https://arxiv.org/html/2502.13069v3)). SAGE-Agent reached higher coverage with **1.39 questions per task** than a baseline asking 2.56, and asked **45-48% fewer questions** than ReAct agents ([SAGE-Agent](https://arxiv.org/html/2511.08798v1)). With a budget that allowed clarifying only 10% of examples, choosing which ones by intent entropy **doubled the gains over random choice** ([Clarify When Necessary](https://arxiv.org/abs/2311.09469v1)). Question quality cuts both ways for humans too: high-quality clarifying questions improved user performance and satisfaction, while **low- and mid-quality ones were harmful** ([Zou et al. 2023](https://research.tudelft.nl/en/publications/users-meet-clarifying-questions-toward-a-better-understanding-of-)).

This evidence fits the goal of asking "as many questions as needed". The literature does not support a small fixed cap; it supports a **value threshold**. The decision-theoretic work agrees on one rule. Score each candidate question by how much it would reduce uncertainty about the build (expected information gain, or the expected value of perfect information, EVPI). Subtract a penalty for aspects already asked about. Ask the best question. Stop when the leading interpretation is confident enough, when the best remaining question is worth less than a threshold, or when the budget runs out. SAGE-Agent puts this into practice as EVPI(q) − λ·(times this aspect was already asked). Raising λ to 0.5 **cut questions 18-27% with under 3% coverage loss** ([SAGE-Agent](https://arxiv.org/html/2511.08798v1)). In a large "room" with many independent high-value aspects, that rule correctly produces many questions. In a small, clear room it correctly produces none. Users tolerate a fair amount: in product search they answered **11-21 clarifying questions on average** but not many more ([Zou, Kanoulas, Liu 2020](https://arxiv.org/pdf/2008.00279)). That number comes from search, not coding, so treat it as a fatigue signal rather than a law.

Three findings shape what each question looks like. First, **closed questions get about 1-2% non-response versus about 18% for open ones**, and high-burden questions triple non-response ([Pew Research](https://www.pewresearch.org/decoded/2021/10/14/why-do-some-open-ended-survey-questions-result-in-higher-item-nonresponse-rates-than-others/)). That argues for multiple choice with a free-text escape. Second, GATE found that having the model generate **concrete edge cases for the user to label** produced more informative specs than user-written prompts, and users found it less effort ([GATE](https://arxiv.org/abs//2310.11589)). "What should happen when the list is empty?" beats "any edge cases?". Third, the hardest ambiguities are the low-level ones. Models catch Units and Numerical Precision more than 65% of the time but catch **Collection Semantics, Comparison Rules, and Ordering & Atomicity under 20%** of the time ([EmergentMind summary](https://www.emergentmind.com/papers/2607.00711)). These belong on an explicit checklist. One risk is real but not well measured: showing AI advice by default **increased a decoy effect** in human decisions ([Behavioural Insights Team](https://www.bi.team/wp-content/uploads/2025/09/How-can-LLMs-reduce-our-own-biases-Analysis-Report.pdf)). So a recommended option should carry its reason, and for irreversible choices the options should be presented neutrally. No controlled study compares batched with one-at-a-time questions, and none measures pass rate as a function of question count. Both are open gaps.

Classic requirements engineering supplies the stopping test that LLM papers lack. Volere's rule says "if a fit criterion cannot be found for a requirement, then the requirement is either ambiguous or poorly understood" ([Volere template](https://www.inf.ed.ac.uk/teaching/courses/seoc/2004_2005/resources/volere-template.pdf)). EARS's five patterns (ubiquitous, state-driven, event-driven, optional-feature, and unwanted-behaviour "If <trigger>, then the system shall…") double as a question generator for behavior and edge cases ([EARS guide](https://alistairmavin.com/ears/)). Google's design-doc practice scales the document to the work: **no doc when the solution is unambiguous, a 1-3 page mini-doc for incremental work, 10-20 pages for large projects**. It also makes explicit non-goals a first-class section ([Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)).

## No tour tool reads every corner and proves it did

Codebase-explanation tools come in five families. None of them aims to explain every corner to a beginner while proving coverage. The bootstrap files mainly prime an agent: Claude Code `/init` "analyzes your codebase and creates a file with build commands, test instructions, and project conventions" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)), and Cline's six-file Memory Bank is re-read at every task ([Cline](https://docs.cline.bot/prompting/cline-memory-bank)). The structural maps compress a repo for a model. Aider ranks tree-sitter symbols in a **1k-token default** map ([aider](https://aider.chat/docs/repomap.html)), and Repomix's `--compress` keeps signatures and drops bodies for a reported **~70% token cut** ([pyshine](https://pyshine.com/Repomix-Pack-Repos-Into-AI-Friendly-Files/)). The hosted wikis, DeepWiki and Google Code Wiki, generate reference pages with diagrams ([Devin docs](https://docs.devin.ai/work-with-devin/deepwiki); [The Register](https://www.theregister.com/2025/11/17/google_previews_code_wiki/)). Cursor-style indexing embeds everything and retrieves chunks on demand ([Cursor](https://cursor.com/blog/secure-codebase-indexing)). Only the fifth family teaches humans. The `code-tour` skill in github/awesome-copilot builds personas such as "New joiner" and "Vibecoder" at three depths: **Quick 5-8 steps, Standard 9-13, Deep 14-18** ([code-tour SKILL.md](https://raw.githubusercontent.com/github/awesome-copilot/main/skills/code-tour/SKILL.md)). PocketFlow Tutorial-Codebase-Knowledge (**12.8K stars**) picks 5-10 core abstractions, orders them into chapters, and writes each chapter in "beginner-friendly language, analogies" ([PocketFlow design](https://github.com/The-Pocket/PocketFlow-Tutorial-Codebase-Knowledge/blob/main/docs/design.md)).

None of them reads everything, and most skip material without reporting it. ECC's `codebase-onboarding` skill says "Don't read everything" and snapshots only two directory levels ([ECC SKILL.md](https://cdn.jsdelivr.net/npm/@colin4k1024/tsp@2.5.2/skills/codebase-onboarding/SKILL.md)). With a `wiki.json`, DeepWiki documents no folder that lacks a page and caps output at **30 pages** ([Devin docs](https://docs.devin.ai/work-with-devin/deepwiki)). PocketFlow skips files over **100KB** by default and caps coverage at 10 abstractions ([PocketFlow](https://github.com/The-Pocket/PocketFlow-Tutorial-Codebase-Knowledge)). The quality complaints follow. An OpenWrt maintainer said DeepWiki "frequently produces hallucinations and factual errors… presented confidently as authoritative documentation" and that its pages "quite rapidly become stale" ([OpenWrt forum](https://forum.openwrt.org/t/important-consideration-deepwiki-ai-generated-docs-may-contain-inaccuracies/249471)). Testers found it decent on simple code but error-ridden on a complex assembler, and strongest where it simply restates existing docs ([lavx news](https://news.lavx.hu/article/ai-generated-documentation-promise-and-pitfalls-in-legacy-code-analysis); [Julia discourse](https://discourse.julialang.org/t/ai-generated-documentation-deepwiki-julia/128447)). No source gives a hallucination rate, so this evidence is anecdotal, but it is consistent.

The best tour designs are verification-heavy and written for the reader. code-tour holds that "a tour pointing to the wrong file or a non-existent line is worse than no tour". It checks every path, line and regex with a validator. Each step uses **SMIG**: Situation, Mechanism, Implication, and a Gotcha the reader "couldn't learn by reading the file". The tour closes on what the reader can now do, not on a recap ([code-tour SKILL.md](https://raw.githubusercontent.com/github/awesome-copilot/main/skills/code-tour/SKILL.md)). ECC adds "Verify, don't guess" (when config and code disagree, trust the code), "Flag unknowns", "Don't copy the README", and a **Where to Look** table that maps "I want to…" to paths ([ECC SKILL.md](https://cdn.jsdelivr.net/npm/@colin4k1024/tsp@2.5.2/skills/codebase-onboarding/SKILL.md)). Anthropic's own docs suggest asking for a project glossary and tracing "the login process from front-end to database". They also recommend delegating exploration to a subagent so that only a summary returns to the main context ([Claude Code common workflows](https://code.claude.com/docs/en/common-workflows)). For big repos they recommend LSP lookups over file scanning and `Read` deny rules for vendored code ([Claude Code large codebases](https://code.claude.com/docs/en/large-codebases)). Two caps limit what a single read can take in: `@file` inclusion stops at **25,000 tokens**, and files over **256KB** are not included at all ([Claude Code common workflows](https://code.claude.com/docs/en/common-workflows)). A tool that claims "every corner" therefore has to cover large files in layers rather than by brute reading.

## Guards are plentiful; plain-language permission explanations do not exist

The permission-explainer slot is open, and the platform already offers a clean hook point for it. In Claude Code, a PreToolUse hook that returns `permissionDecision: "ask"` puts its `permissionDecisionReason` text **inside the permission prompt the user sees**. For `allow`, the same text goes only to the debug log, and for `deny` it goes to Claude. Hooks that time out fail open: "don't count on a stalled hook to act as a gate" ([Hooks reference](https://code.claude.com/docs/en/hooks)). Auto mode now handles most prompts with a classifier. When it blocks something, the user usually sees a rule label such as `[Data Exfiltration]` "rather than a written explanation" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). The classifier misses **17% of real overeager actions** ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). The Explanatory and Learning output styles teach code design through Insight blocks and `TODO(human)` exercises. They say nothing about what a command will do to the machine, and they are "instructions Claude follows, so nothing enforces it" ([Output styles](https://code.claude.com/docs/en/output-styles)).

Dangerous-command guards are mature and should be reused, not rebuilt. dcg (**~6.4k stars**) ships 50+ rule packs and an "explain mode" across Claude Code, Codex, Gemini, Copilot and Cursor ([dcg](https://github.com/Dicklesworthstone/destructive_command_guard)). cc-safety-net parses commands semantically, catches `curl … | bash` hidden inside `bash -c`, and supports 16 CLIs, but says only that "the agent is told why" ([cc-safety-net README](https://cdn.jsdelivr.net/gh/kenryu42/cc-safety-net@main/README.md)). Copilot CLI's `/explain <command>` shows that plain-language command explanation is a solved, on-demand capability. It is simply not wired into approvals ([Copilot CLI docs](https://docs.github.com/copilot/using-github-copilot/using-github-copilot-in-the-command-line)). Cline's model-set `requires_approval` flag and Codex's reviewer agent tier risk, but they act as binary gates and explain nothing to a human ([Cline](https://docs.cline.bot/features/auto-approve)).

The human-factors evidence says that explaining every prompt in the same way would make things worse. Anthropic reports that **users accept 93% of manual permission prompts** and calls this "approval fatigue" ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). fMRI studies by Anderson, Vance and colleagues found visual processing of a warning **dropped sharply after the second exposure**. "Polymorphic" warnings, whose appearance varies, held attention much longer in a three-week field study ([MISQ 2018](https://misq.umn.edu/pub/skin/frontend/default/misq/pdf/V42I2/14124_RA_VanceJenkins.pdf)). A 2026 modeling paper finds safety follows an **inverted U against escalation rate** once reviewer fatigue grows with load, and reviewers agreed only moderately on what is risky (**κ = 0.52**) ([Turan, arXiv 2606.08919](https://arxiv.org/abs/2606.08919)). Explanations therefore have to be rare, scaled to risk, and visually distinct at the top tier. They must also come with fewer prompts, not more. One critique fairly notes that some of the 93% reflects informed trust rather than fatigue ([Procurement Tidbits](https://procurementtidbits.substack.com/p/human-in-the-loop-still-let-4-in-10)). And no study yet tests whether plain-language explanations raise juniors' catch rates, so this mode is the least evidence-backed of the three.

## A parameterized design for plan-every-corner

The design below combines the strongest pieces of prior art. It marks which choices rest on evidence and which are judgment. Many existing skill collections already contain overlapping pieces (one-at-a-time clarification, CodeTour generation, codebase onboarding, destructive-command brakes), so the design borrows their best parts rather than competing with them.

### Modes and the triage gate

The skill exposes three modes: **Tour** (explain an existing codebase), **Interview** (understand a new room before building), and **Explain** (risk-scaled permission explanations). Interview always starts with a triage step modeled on superpowers' Spike/Bounded/Architectural classification ([superpowers](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)). The skill states the tier aloud, the user can override it, and hidden complexity can only move the tier up. Before the first question, a silent investigation pass reads the repo, as Cline's deep planning does ([Cline](https://docs.cline.bot/features/deep-planning.md)). Its job is to answer every navigational and convention question without asking, because Ambig-SWE shows this is what lets strong models ask half as many questions ([Ambig-SWE](https://arxiv.org/html/2502.13069v3)). The skill then writes a draft spec with guesses, as Spec Kit `/specify` does, so the questions target gaps in a concrete document rather than a blank page.

### Size tiers and question budgets

Budgets are **soft checkpoints, not caps**. When a budget is reached, the skill shows the coverage ledger and asks "continue, or build with the remaining items as stated defaults?" This keeps the "as many as needed" goal while giving users the exit that complaining users asked for. *(The final skill dropped these pauses: the user can say "build now" at any time instead.)*

| Tier | Signal | Expected questions | Checkpoint every | Spec size |
|---|---|---|---|---|
| T0 Spike | unambiguous fix or tweak | 0-2 | n/a | none; assumptions stated in chat |
| T1 Small feature | one behavior, one surface | 2-6 | 6 | ½-1 page |
| T2 Medium feature | several behaviors, data touched | 6-15 | 8 | 1-3 pages |
| T3 Large feature | new data model, APIs, cross-cutting concerns | 15-30 | 10 | 3-8 pages |
| T4 New project | greenfield, multiple subsystems | 25-60, split per sub-room | 10 per sub-room | split if >10-20 pages |

The anchors are evidence-backed: about 1-4 questions per scoped task ([SAGE-Agent](https://arxiv.org/html/2511.08798v1); [Ambig-SWE](https://arxiv.org/html/2502.13069v3)); 20-60 observed for whole features ([VelvetShark](https://velvetshark.com/stop-prompting-claude-code-let-it-interview-you)); user tolerance of 11-21 per sitting ([Zou et al. 2020](https://arxiv.org/pdf/2008.00279)); and Google's none / 1-3 / 10-20 page sizing ([Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)). The exact boundaries are judgment calls that need tuning with real sessions. T4 follows superpowers' rule: decompose into sub-rooms before spending any questions on details, then interview each sub-room in turn.

### Question taxonomy mapped to the room

Every candidate question falls into one ledger row. The rows merge Spec Kit's ten categories ([clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)), EARS behavior patterns ([EARS](https://alistairmavin.com/ears/)) and ClarifyCodeBench's ambiguity types ([EmergentMind](https://www.emergentmind.com/papers/2607.00711)).

| Room aspect | Ledger rows | Typical question form |
|---|---|---|
| Purpose | goal, users/roles, success metric | open (intent is the user's alone) |
| Size | scope boundary, **explicit non-goals**, data volume/scale, phasing | multiple choice |
| Contents | entities, identity/uniqueness, lifecycle/states, integrations and their failure modes | multiple choice |
| Behavior | EARS event / state / optional variants; UX flow incl. empty, loading, error states | edge-case scenario ("when X, should…?") |
| Edge cases | EARS unwanted-behavior; empty/zero/max/malformed sweep; **ordering & atomicity, comparison rules, collection semantics**, ranges, units, precision, output format; concurrency, permissions | scenario labeling |
| Constraints | stack, hosting, performance, security/privacy, observability, compliance | multiple choice, often defaulted |
| Terminology | glossary, vague adjectives ("fast", "intuitive") | short answer |
| Done | fit criterion per requirement, definition of done | confirm a proposed test |

The skill never asks implementation questions the user cannot answer. It decides those itself and records them as assumptions, a rule backed by the turns DeepSeek wasted in Ambig-SWE ([Ambig-SWE](https://arxiv.org/html/2502.13069v3)). The bolded data-semantics rows are mandatory checks because models catch them less than 20% of the time on their own.

### Selection, format and ordering

A question is asked only when four conditions hold. The user alone holds the answer. The plausible interpretations would change the code or tests materially, which is a prompt-level stand-in for EVPI. The aspect has not been asked before, mirroring SAGE's redundancy penalty. And the user can realistically answer it. Everything else becomes a **stated default** in an Assumptions section, as Spec Kit does. Questions are ordered hardest-to-reverse first (scope, data model, core flows), so their answers prune later questions. That ordering is a design inference, not a measured result. The format is closed multiple choice with 2-4 options plus "Other", per the Pew non-response evidence and AskUserQuestion's limits. Each question includes a one-line "why it matters" and, for reversible choices, a **Recommended** option with its reason; a reply of "yes" accepts it, as in Spec Kit. For irreversible or high-stakes choices, the options are shown neutrally with their consequences, to limit the default effect BIT observed. Independent closed questions go **up to four per AskUserQuestion call**. Dependent and open questions are asked one at a time, because what a later question is worth depends on earlier answers. Every checkpoint also offers "Tell me what you're assuming", the anchoring countermeasure critics proposed ([Robots Ate My Homework](https://robotsatemyhomework.substack.com/p/penny-moves-claude-askuserquestion)). Batch size and the assumptions option are judgment calls.

### Stopping rule

The interview stops when **all** of the following hold. Every ledger row is Resolved, Discovered, Defaulted or N/A. Every requirement has a measurable fit criterion, per Volere ([Volere](https://www.inf.ed.ac.uk/teaching/courses/seoc/2004_2005/resources/volere-template.pdf)). No open aspect has interpretations that would change code or tests materially, which mirrors SAGE's EVPI-below-threshold test ([SAGE-Agent](https://arxiv.org/html/2511.08798v1)). And every mandatory data-semantics row has been checked. The user can also stop at any time with "build now". Unresolved rows then move to Assumptions and are flagged as risks. If the triage pass finds nothing material, the skill says so and proceeds, as Spec Kit's "No critical ambiguities detected" exit does. The structure of this rule is evidence-based; the thresholds are judgment.

### Output artifacts and the coverage ledger

Interview produces **one** `SPEC.md`, because users rejected the many-file alternative ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Its sections are Goal, Non-goals, Glossary, Requirements in EARS form each with a fit criterion, Edge cases, Assumptions (defaults taken), a Clarifications log written after every answer, the Coverage ledger, and the Definition of done. The build then runs in a **fresh session from SPEC.md**, and a reviewer pass checks the diff against it, which follows Anthropic's documented workflow ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The ledger is a table with status Resolved (asked), Discovered (found in the code), Defaulted (assumed, with a reason), N/A or Open. It lives in the file, not in chat, and is printed only at checkpoints and at the end. Tour mode uses the same ledger shape keyed by directory: Explained, Mentioned, Skipped (with a reason) or Unknown. That turns "every corner" into something the user can check instead of a promise.

### Tour mode parameters

Tour reads in three levels so that full coverage stays affordable. **Level 0** inventories every file, with path, size and token estimate, through Glob and gitignore-aware listing. **Level 1** outlines source files through LSP symbols or signatures, the Aider and Repomix idea. **Level 2** reads in full only the entry points and the ranked core path. Each top-level directory is explored by a subagent that returns a summary, per Anthropic's guidance ([Claude Code common workflows](https://code.claude.com/docs/en/common-workflows)). The output is a `TOUR.md` index kept under about **200 lines**, the size Claude's memory guidance gives for adherence ([Claude Code memory](https://code.claude.com/docs/en/memory)), plus chapter files. Chapters are ordered from foundational concepts to advanced ones with analogies, as PocketFlow does. Each step uses SMIG with a verified `file:line`. The tour includes exactly one end-to-end request trace, a glossary, a Where to Look table, and a closing section on "what you can now do". Depth follows code-tour's Quick / Standard / Deep (5-8 / 9-13 / 14-18 steps). The README is treated as a claim to verify, not a source. Every path and line is validated before output. The cache is stamped with the commit SHA so a later session re-tours only directories that changed. Defining "every corner" as "every directory accounted for in the ledger" is a judgment call; the alternative of reading every line deeply is not affordable.

### Explain mode parameters

Detection reuses dcg or cc-safety-net. A thin PreToolUse layer sorts each call into four tiers: **read-only, reversible, hard-to-reverse, irreversible**. Read-only and reversible calls are left to auto mode or allow rules, so they produce no prompt and the prompt count drops. Hard-to-reverse and irreversible calls return `ask` with a `permissionDecisionReason` that leads with a reversibility label ("can be undone with `git reflog`" or "cannot be undone"). It continues with a What / Why / Changes / Undo card in everyday language, and the irreversible tier gets a visually distinct format, applying the polymorphic-warning finding. The "Why" comes from Claude's narration before the call, required by the skill, and is grounded in the literal command and guard verdict so that injected text cannot pass as a reason. The risks to design around are that `ask` overrides auto-approval, so the matcher must stay narrow, and that hook timeouts fail open ([Hooks reference](https://code.claude.com/docs/en/hooks)). Rendering limits of `permissionDecisionReason` are undocumented and need a local prototype.

### Token-saving tactics

The cheapest question is the one answered by reading the repo first. The coverage map and spec are written to disk once and updated incrementally, so they are not regenerated each turn (Spec Kit's pattern). Batching up to four closed questions per call saves round trips. One-word "yes" acceptances keep answers short. Exploration happens in subagents, while the interview itself stays in the main thread because AskUserQuestion is unavailable in subagents. The build starts from SPEC.md in a fresh session rather than the interview transcript. T0 tasks skip the interview and the tour entirely. Tour caches keyed by commit SHA, with short indexes and on-demand topic files, avoid re-exploring the repo. One measured caution: interaction made agents more effective but not more efficient, with Sonnet 4's steps rising from **65 to 75** ([Ambig-SWE](https://arxiv.org/html/2502.13069v3)). The token payoff comes from avoiding failed builds, not from a cheaper planning phase.

### Reuse versus build, and evidence versus judgment

| Component | Decision | Basis |
|---|---|---|
| Question selection (taxonomy scan, Impact × Uncertainty, recommendation, write-back) | **Reuse** Spec Kit `/clarify` logic, uncapped | Evidence: strongest published design; caps removed per user requirement |
| Explore-before-ask, ask only user-held info | **Reuse** pattern | Evidence: Ambig-SWE, SAGE-Agent |
| Data-semantics checklist | **Build** (small) | Evidence: ClarifyCodeBench miss rates |
| EARS requirements + fit criteria + non-goals | **Reuse** format | Evidence: EARS, Volere, Google design docs (practice, not LLM-validated) |
| Size tiers and budget numbers | **Build** | Judgment anchored to cited ranges |
| Batch size, checkpoint cadence, neutral options for irreversible choices | **Build** | Judgment (no controlled study exists) |
| Fresh-session build + reviewer against SPEC.md | **Reuse** Anthropic workflow | Evidence: official practice; no outcome study |
| Tour verification, SMIG, personas, depth levels | **Reuse** code-tour | Evidence-informed practice; no comparative user study |
| Three-level inventory + directory coverage ledger | **Build** | Judgment responding to documented silent skips |
| Dangerous-command detection | **Reuse** dcg / cc-safety-net, or an existing destructive-command guard | Evidence: mature, multi-agent |
| Risk-tiered human explanation layer | **Build** | Habituation evidence supports the format; effect on juniors untested |

## Conclusion

The research reframes the original question. "How many questions?" is the wrong parameter. The right one is the value threshold a question must clear. Fixed caps like Spec Kit's five are a cost-control shortcut, and "interview until complete" works only when completeness can be measured. Volere's fit-criterion test plus a coverage ledger supplies that measure. With both in place, an uncapped interview stays efficient: in a rich room it asks thirty sharp questions, and in a simple one it asks none. The same logic connects all three modes. Tour's directory ledger, Interview's requirement ledger and Explain's risk tiers each replace an implicit judgment ("I covered it", "I understood it", "this is safe") with an explicit one the junior can see and check. That visibility is how a good senior developer works.

The largest open risk is that no published study yet ties any of this to one-shot build success with real users. The evidence comes from LLM-simulated users, survey methodology and security-warning research, not from interviews of developers building features. The skill should therefore record its own telemetry: questions asked per tier, how often users choose "build now", and how many post-build fixes trace back to a Defaulted ledger row. Those numbers would turn this report's judgment calls into tuned parameters within a few dozen sessions.
